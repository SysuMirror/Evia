Internal maintenance only; do not ship this file in customer integration packages.

Read AGENTS.md and docs/standards/ui.md. Complete and verify backend behavior first. Build shared primitives, tokens and layouts in packages/design-system before composing apps/console pages. Use generated contracts and the shared API client.

Ordinary UI controls must use Evia-owned React components and semantic HTML. The existing access pages use the native foundation; follow docs/plans/native-ui.md for subsequent delivery. Put tokens in CSS variables, use native control props and explicit React state, and keep forms based on native submission/validation with application field errors. Do not reintroduce Ant Design underneath wrappers or reproduce its imperative form engine. Retain the existing router, server-state and API boundaries. Mature specialized libraries are appropriate for complex capabilities such as charts when their accessibility, maintenance and bundle impact are documented; load them on demand behind shared Evia components.

Implement the interaction-state matrix in docs/standards/ui.md. Pointer and keyboard actions must have matching native semantics, with single submission, event cancellation and stable accessible names. Verify combined hover/focus/error styles, disabled/busy/read-only controls, labels and live feedback. Pending work, changing props, unmounting, nested dialogs and expiring notifications must not publish stale feedback or steal focus. Use the isolated browser component fixture for shared controls absent from current business pages; keep its entry out of the production build and retain real-backend page tests.

Design for a compact developer console: cool whites, slate text, restrained blue accents, readable tables and real actions. Reuse DesignProvider, Brand, WorkspaceShell, AuthLayout, PageHeading, DataSurface and PaginationBar. Desktop header is 64 px, sidebar 220 px and content padding 24 px; page titles are 22–24 px. Use the approved logo asset, not a substitute letter mark. Use a white main workspace, pale neutral sidebar, softly rounded light-gray result cards, quiet navigation pills and one vivid primary action. Resource tables remain white and readable. AuthLayout uses a restrained headline, original pastel abstract visual and white rounded form on desktop, collapsing to the form on mobile. Record only Evia-owned design decisions; do not include names, screenshots or branding from supplied interface references in repository files or commit messages. Preserve required dependency attribution. Avoid promotional paragraphs, decorative data cards and mock metrics.

Page headings contain the title and relevant actions. Do not add English eyebrows, generic explanatory subtitles, sidebar explanations or duplicated table-section titles. Remove stable UUIDs from ordinary resource lists; keep them copyable in details. Put useful help next to the relevant control, in an empty state or in recovery feedback. Use direct Chinese copy with commas between parallel status facts, no middle-dot separators. Document titles use the plain brand “Evia 映途”.

Do not equate concise presentation with a visually empty interface. Use a clear hierarchy of navigation, compact working controls and actual results. Analysis results should appear within the ordinary desktop viewport; long configuration editors belong in labeled dialogs with their own validation and focus recovery. Keep a readable draft summary and distinguish it from the submitted result snapshot. Real tabs must own their content, persistent toggles must look selected, and notification queue eviction must respect both pointer hover and keyboard focus. A passing functional test does not establish visual quality: inspect the final screens and compare result placement and mobile context height against the baseline.

Preserve project context and readable hierarchy. Every asynchronous surface needs loading, empty, success, permission and error handling. Forms retain input on failure; concurrent edits remain recoverable. Include visible labels, field feedback, stable accessible names for busy actions, focus management, safe confirmation defaults, keyboard navigation and responsive layouts. Keep every implemented action reachable on mobile; table overflow stays inside its surface.

Run type checking and production build, then verify the feature in a real browser against a real backend. Exercise successful and failed operations, keyboard interaction and narrow viewports; assert no uncaught browser exceptions. Visually inspect fresh desktop and mobile screenshots for density, hierarchy, overflow and dialogs before claiming completion. Update PROGRESS.md with actual evidence and commit the reusable foundation separately from business pages.

For the native migration, capture the current production bundle and interaction baseline first. Compare initial JavaScript/CSS, lazy chunks and browser measurements under the same conditions after migrating. Document conditions and results, investigate regressions, and avoid treating dependency removal or a raised warning threshold as performance evidence. Keep pending migrations explicit in PROGRESS.md.
