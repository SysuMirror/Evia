# Zipf 幂律身份分布验证记录（2026-11-13）

## 范围

长尾分布演练（`long-tail-distribution-2026-11-13.md`）用两段均匀轮转
合成了头尾数量级差异，但不是幂律。本切片把负载升级为数学上真正的
Zipf 分布：身份秩 r 的概率正比于 `1/r^s`（s=1.0），经真实
Kafka→ingest-worker→ClickHouse 落库后，同时验证**逐身份整数分配精确**
与**秩-频双对数斜率符合幂律**，推进 feature-coverage 中「真实 Zipf 采样
分布」剩余项。

本切片不改动任何生产 Go 代码；新增物为一个集成测试、一个演练脚本与纯
逻辑单测、文档，并把新演练注册进统一准备度套件（套件由九扩为十）。

## 确定性 Zipf 分配规则（跨语言同构）

Go 装载器与 Python 评估器实现同一规则，不共享 fixture 文件：

1. 权重 `w_i = 1 / i^s`（一基秩 i=1..500，s=1.0）；
2. 配额 `q_i = 4000 * w_i / Σw`；
3. Hamilton 最大余数法取整：先取 floor，再按余数从大到小补齐，使整数
   席位之和严格等于 4000；余数并列时按最低秩优先（两端都用稳定排序）。

跨语言浮点同构获得实证：Go 与 Python 对同一参数算出的双对数斜率均为
`-1.029515`（六位小数一致），抽样秩计数完全相同。

## 验证的不变量

1. **全覆盖与精确计数**：500 个身份全部至少 1 个事件；6 个抽样秩（热/
   中/冷：1、2、3、11、101、500）的 ClickHouse 计数严格等于 Hamilton
   分配期望；`uniqExact(uid)=500`。
2. **幂律形状**：对 `(ln rank, ln count)` 做最小二乘拟合，斜率
   -1.0295，与理论值 -1.0 的偏差在 0.15 容差内（偏差来自整数取整噪声，
     纯函数单测另用无噪声精确幂律验证斜率恢复到 -1.5）。
3. **Top-K 排序**：`GROUP BY uid ORDER BY count() DESC LIMIT 5` 返回的
   身份顺序与分配的前五热秩严格一致。
4. **有界读延迟**：热点/深尾/基数三类查询各 12 次，p95 全部在 10 秒
   预算内，并从 `system.query_log` 报告峰值内存。

## 先红后绿

- 初版辅助函数引用了不存在的 `splitLines`，改为标准库 `bytes.Split`；
- Hamilton 余数排序必须用稳定排序（`sort.SliceStable`）才能与 Python
  稳定排序的并列裁决一致，否则浮点余数接近时两端分配可能分叉。

## 边界与诚实声明

- 这是**参数化标准 Zipf**（s=1.0），证明存储层对真实幂律形状的计数与
  查询正确性，但指数是人为选定而非从生产数据拟合；生产验收仍需用真实
  事件采样估计 s 后重跑同一套演练。
- 单 broker、单 ClickHouse、4000 事件规模：延迟是单机小数据集基线，
  不外推多节点或千万用户量级；存储层直连 CH，绕过公开 API 鉴权/排队。
- 整数取整使观测斜率偏离理论值约 3%，容差 0.15 已覆盖；若提高指数或
  缩小事件/身份比，需重新评估取整噪声与全覆盖前提。
- 本证据不改变 514/728 读侧失败记录；生产拓扑分发（跨故障域/TLS）、
  长保留期与多租户隔离容量仍需独立专项。
