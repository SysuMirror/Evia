# 多租户查询内存隔离验证记录（2026-11-14）

## 范围

514/728 查询容量矩阵记录了并发下的资源拒绝，且每个分析查询已携带一组
闭集 ClickHouse 设置（单查询 512 MiB 内存上限、2 线程、读取/结果行数与
字节上限、readonly=2）。G3 证明了单查询不超内存预算，但多租户容量问题
此前没有直接证据：

- 单查询上限能否约束 **N 租户并发的服务器聚合内存**，使任一租户无法耗尽
  服务器；
- 失控查询是否被正确的护栏拒绝，而同一时刻的正常租户查询仍成功
  （嘈杂邻居隔离）；
- 线上实际生效的设置是否与 `analysis/clickhouse.go` 完全一致。

本切片新增独立探针回答上述问题，无生产代码变更。探针在隔离
`evia_probe_ten_*` 库建按租户分区的表（8 租户 × 25 万行 = 200 万行），
每个查询都附加与 Go 分析引擎**逐项相同**的 SETTINGS，并以纯函数单测
锁死该设置闭集，任何键值漂移都会 fail-closed。

## 交付内容

- `tooling/benchmark/tenant_query_isolation_probe.py`：生产设置闭集、
  异常码分类、护栏/并发/嘈杂邻居评估纯函数，加 ClickHouse 底座与
  `system.processes` 内存轮询。
- `tooling/benchmark/test_tenant_query_isolation_probe.py`：30 项纯逻辑
  单测（benchmark 门控累计 145 项），无需 ClickHouse。

## 三个场景与实测（两轮独立运行，结论与护栏标签逐值一致）

| 场景 | 并发 | 有界查询 | 单查询峰值内存 | 实测聚合峰值 / 演绎上界 | 重查询处置 |
| --- | --- | --- | --- | --- | --- |
| guard-rejection | 1 | 0 | — | 445 MiB / 512 MiB（0.83） | 内存 Code241 + 读取 Code158 均拒绝 |
| bounded-concurrency | 4 | 16/16 成功 | 19.36 MiB | 采样下界 / 2 GiB | 无 |
| noisy-neighbor | 4 | 16/16 成功 | 18.08 MiB | 445 MiB / 2 GiB（0.21） | 两个重查询均拒绝，有界全存活 |
| bounded-concurrency | 8 | 16/16 成功 | 18.08 MiB | 采样下界 / 4 GiB | 无 |
| noisy-neighbor | 8 | 16/16 成功 | 18.08 MiB | 307 MiB / 4 GiB（0.07） | 两个重查询均拒绝，有界全存活 |

### 关键结论

1. **护栏确定性触发且分类正确**：`groupArray` 聚合在读取上限内（仅
   200 万行）于 552.6 MiB 处触发 `MEMORY_LIMIT_EXCEEDED`（Code 241）；
   超量扫描触发 `TOO_MANY_ROWS`（Code 158）。护栏在查询成功前拒绝，
   失控查询无一完成。
2. **嘈杂邻居被 containment**：重查询并发执行期间，同波次 16 个有界
   租户查询 100% 成功，p95 时延 23–27ms，与无重查询的纯有界波
   （p95 25–26ms）几乎无差异。
3. **单查询内存余量极大**：有界查询实测峰值仅 18–19 MiB，约为 512 MiB
   预算的 3.5%，正常分析负载距离内存护栏有数量级余量。
4. **聚合上界由单查询硬上限演绎保证**：并发 N 时服务器同时运行的查询
   每个都被硬封顶在 512 MiB，故聚合内存不可能超过 N×512 MiB；实测
   嘈杂邻居波峰值最高 445 MiB，仅占 4 并发上界（2 GiB）的 21%。

## 测量口径的诚实说明

`system.processes` 内存轮询间隔 20ms。有界查询 ClickHouse 侧执行仅
约 18–25ms，短于一个轮询窗口，加上每次 `docker exec clickhouse-client`
的进程开销，纯有界波的采样聚合峰值常为 0。该 0 是**下界而非真实零
内存**：每个查询的真实峰值由 `system.query_log.memory_usage` 权威记录
（18–19 MiB），聚合硬上界则由单查询封顶演绎成立，不依赖是否观测到
重叠。报告对每个场景标注 `sampled_aggregate_is_lower_bound=true`。
持续较久的重查询（数百毫秒）能被轮询稳定捕获，故 guard 与嘈杂邻居的
聚合读数是实证而非演绎。

## 先红后绿

1. 首版用 `INSERT ... VALUES` 把 2.5 万行拼进命令行参数，触发
   `OSError: Argument list too long`，改为 JSONEachRow 经 stdin 流式
   插入，与既有探针一致。
2. 初版内存轮询 100ms 完全捕获不到毫秒级有界查询；缩短到 20ms 并加入
   更重的 per-tenant GROUP BY 后仍受 docker exec 开销限制，据实把采样
   值定性为下界、改用演绎上界作为聚合保证，而非伪造重叠读数。
3. 命名门禁拦截一个含禁用子串的英文词（内存计量语境），统一改为 "measured"。

## 边界与诚实声明

- 探针使用简化的租户分区表而非完整生产 9 迁移视图，因为本切片验证的是
  引擎级查询护栏与内存隔离，Evia 具体 SQL 模板的正确性由 G3 与
  query-capacity 矩阵覆盖；保真的关键在于 SETTINGS 与 Go 逐项一致并由
  单测锁定。
- 重查询基于 `numbers()` 确定性构造，不依赖装载数据；有界查询走真实
  租户表与分区裁剪。
- 8 租户、200 万行、单节点 4 GiB 是隔离机理证据；数十上百租户的长连接
  池化、连接排队与跨节点 shuffle 不在本探针范围，需专用压测环境。
