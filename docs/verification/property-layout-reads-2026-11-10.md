# Property token 布局的物理读测量（门控未通过）

执行日期：2026-11-10，UTC。本文记录 `property_tokens Map(String,String)` 派生布局在真实 ClickHouse 26.8.36.3 上的受控物理读测量。结论先行：**该布局在本测量画像下没有通过设计文档规定的物理读门控，不进入 backfill 与生产切换**。测量只评估物理读与内存，不重复已经由集成测试证明的结果等价性。

## 测量条件

- 独立一次性库 `evia_probe_reads`，依次应用迁移 001、003、006、007，测完即删。与生产相同的 `max_threads=2`，每次查询前执行 `SYSTEM DROP MARK CACHE`；未关闭操作系统页缓存，因此同时报告确定性的 SelectedMarks。
- 两组各 100,000 行、共 200,000 行，文档结构完全相同：24 个约 100 字节的定宽字符串属性加 1 个数值属性 `metric_07`（取值 0–99 均匀分布）。`legacy_doc` 组为版本 0、空 map 的旧写入画像；`layout_map` 组为版本 1、携带完整派生 map 的新写入画像。JSONEachRow 载荷 1.02 GiB，导入后 `OPTIMIZE ... FINAL` 合并为单分片。
- 测量直接针对 `event_facts_raw`，刻意排除 `event_facts` 视图的 argMin 聚合成本——后者是独立的已知瓶颈。视图路径另见下文的临时盘观察。每类查询 5 次重复，指标取自 `system.query_log` 的 `QueryFinish` 行，五次结果完全一致。
- 合成数据的键名固定、字符串定宽且高度重复，对单个 String 列的压缩极其有利，属于对 Map 布局偏不利的画像；真实分布下差距可能收窄，结论不外推到所有数据分布，但 v0 fallback 的额外开销与数据分布无关。

## 静态存储

单分片内列文件实测（200,000 行，其中 100,000 行的 map 已填充）：

| 列 | 压缩后 | 未压缩 |
| --- | ---: | ---: |
| `properties_json` | 30.0 MiB | 943.1 MiB（约 31 倍压缩） |
| `property_tokens`（keys + values + 偏移/标记） | 约 2.5 MiB | — |
| `property_layout_version` | 约 1 KiB | — |

Map 列静态体积约为文档列的十二分之一，但查询成本并不由静态体积决定。

## 查询物理读与内存

过滤谓词：数值属性 `metric_07 > 50`，两组结果均为 49,000 行，证明语义等价。下表为 5 次重复的稳定值：

| 查询路径 | read_bytes | SelectedMarks | peak memory | 耗时中位数 |
| --- | ---: | ---: | ---: | ---: |
| 旧路径：文档列 JSON 提取（v0） | 285,295,706 | 35 | 271,582,115 | 377 ms |
| 新路径：token map 合成文档（v1） | 361,477,048 | 63 | 767,488,575 | 396 ms |
| 新 gated SQL 跑在 v0 数据（fallback 分支） | 286,297,226 | 35 | 465,460,203 | 520 ms |

字符串分组（`segment_03`）呈现同一方向：旧路径 285,289,976 字节 / 34 marks，新路径 371,689,967 字节 / 63 marks。基线 `count()` 两路均为个位数字节，证明差异完全来自属性读取而非扫描框架。

### 发现

1. **v1 map 查询比文档路径多读 26.7% 字节、多选 80% 的 mark、峰值内存高 183%**。Map 在 MergeTree 中存为并行的键数组与值数组并附带多个独立数据流，点查仍按 granule 读取整个 Map 列；高压缩比的单个 String 列在该画像下反而更省。
2. **当前生产数据全部为 v0，而 gated SQL 即使恒走 fallback 分支，峰值内存也从约 259 MiB 升到约 444 MiB（+71.4%），耗时 +38%**，读字节基本持平（+0.4%）。这会直接恶化百万矩阵中导致失败的 512 MiB 内存预算（错误码 241），且在任何 backfill 完成前普遍存在。
3. 视图层面的独立观察：对同一 10 万行宽文档组执行 `event_facts` 聚合时，携带 Map 的 28 元素 argMin tuple 预留约 722 MiB 临时空间，超出容器 512 MiB 临时盘配额，全部以错误码 243 失败；不含属性访问的基线计数也无法完成。
4. 结论是**存储省、查询贵**：Map 方案以写入放大和查询内存换取了静态体积，却没有换来设计目标中的扫描字节下降。

## 处置决定与边界

- 不构建 backfill、不做生产读取切换；在出现可通过同一门控的替代布局前，006/007 仅作为 schema 基础保留，默认值保证旧 parts 与旧写入者零行为变化。
- 已上线的 reader 切换应回退至文档路径，避免 v0 数据上普遍承担 +71% 的内存开销；等价性与混合获胜回退测试保留为后续布局的现成验证资产。
- 本文不判定所有替代布局失败。后续候选（有限热键的专用列、在真实低压缩比分布上复测、或带词法等价护栏的 JSON 子列）必须复用本次的数据集与指标口径重新过门控；静态体积、写入 CPU、合并成本和混合版本回退语义仍需一并测量。
- 合成数据的重复度偏高、单机 20 万行、未含完整视图并发矩阵，因此本文是门控裁决与方向性证据，不是生产容量声明。
