# 稳态混合读写容量验证记录（2026-11-13）

## 范围

补齐 `feature-coverage.md` 容量工程中的「持续混合读写」缺口。既有证据分处
两端：514/728 矩阵在**冻结数据集**上测读并发，积压恢复演练在**无读流量**
下测写故障，二者都没有「边持续写入、边并发查询」的稳态证据。本切片在真实
Kafka→ingest-worker→ClickHouse 管线上同时驱动持续摄取与并发分析查询，
验证存储层在混合负载下的精确一次、读可用性、单调性与延迟/内存边界。

本切片不改动任何生产 Go 代码；新增物为一个集成测试、一个演练脚本与纯逻辑
单测、文档。

## 交付内容

- `backend/internal/pipeline/mixed_workload_integration_test.go`：
  `TestSteadyMixedReadWrite`（integration 标签，`EVIA_TEST_MIXED_DRILL=1`
  门控）。一个生产 `Worker` 持续消费真实 Kafka 并写 ClickHouse，同时 4 个
  读协程对 `event_facts` 视图轮流执行三类有界分析（总数、按 event_key
  分组、UID 切片，均带 `max_execution_time=10`），用 SQL 注释标记后从
  `system.query_log` 取峰值内存。
- `tooling/ha/mixed_workload_drill.py` 与 16 项纯逻辑单测（纳入
  `make ha-tools-test`）：与 Go 同约定的百分位、单调非降判定、读成功率、
  报告解析与不变量评估。

## 验证的不变量

1. **精确一次落地**：混合负载结束时去重视图计数严格等于生产事件数，
   raw 表不少于生产数（允许重放产生的额外物理行）。
2. **零读失败**：写压力持续期间所有读请求成功，读成功率 1.0；任何读错误
   都判失败。
3. **单调非降**：每个读协程按序观察到的总数只增不减（insert-only 工作
   负载），出现下降即失败——捕获读取到中间不一致状态的回归。
4. **有界读延迟与内存**：p95 读延迟必须在每查询 10 秒执行预算内，并报告
   `system.query_log` 的峰值内存，作为容量矩阵的一个实测单元。

## 先红后绿（测试自身缺陷修正）

- 读查询未显式 `FORMAT JSONEachRow` 时 ClickHouse 返回裸值，先补格式；
  JSONEachRow 是逐行单对象而非数组，解析器改为读首行对象；分组结果首列
  是字符串 `event_key`，解码目标改为 `map[string]any` 并跳过非数字列。
- worker 取消断言改用 `errors.Is(context.Canceled)`，与既有集成测试对齐。
- 百分位单测最初误用「中位数」直觉（4 样本 p50=2），实际 Go/Python 统一
  采用零基 floor 索引 `len*pct/100`（4 样本 p50 索引 2 即值 3），以代码
  约定为准修正测试。

## 环境

- 开发测试栈：Apache Kafka 4.4.0（单 broker，`127.0.0.1:19092`）、
  ClickHouse 26.8.36.3（`127.0.0.1:18123`），当前运行中的 dev 容器。
- 负载：600 事件分 20 批、每批 30、批间隔 250ms（约 5 秒稳态写窗口）；
  4 个读协程全程并发，三类查询轮转，单查询 `max_execution_time=10`。
- 每次运行使用唯一后缀 topic/消费组/数据库，由 `t.Cleanup` 清理；两轮后
  无残留主题或数据库。

## 真实演练结果

命令（工具链激活，凭据经环境变量传入）：

```
python3 tooling/ha/mixed_workload_drill.py
```

两轮独立运行均 `status=passed`：

| 指标 | 第一轮 | 第二轮 |
| --- | --- | --- |
| 生产/落地事件 | 600 / 视图 600 / raw 600 | 同左 |
| 写吞吐（到排空） | 115.9 事件/秒 | 114.6 事件/秒 |
| 并发读协程 | 4 | 4 |
| 读样本总数 | 974 | 993 |
| 读失败 | 0（成功率 1.0） | 0（成功率 1.0） |
| 读 p50 | 10ms | 10ms |
| 读 p95 | 66ms | 67ms |
| 三类查询各自 p95 | 66 / 64 / 68 ms | 67 / 65 / 68 ms |
| 单调非降读协程 | 4/4 | 4/4 |
| query_log 峰值内存 | 15,025,451 字节（约 14.3 MiB） | 同左 |
| 残留主题/数据库 | 无 | 无 |

## 边界与诚实声明

- 这是**存储层**混合负载：读直接打 ClickHouse HTTP，绕过公开 API 的鉴权、
  排队与异步作业轮询；端到端 API 延迟仍以 514/728 矩阵为准，两者互补不
  互相替代。
- 单 broker、单分区、单 ClickHouse 节点、4 读协程与 600 事件小数据集：
  p95 毫秒级结果反映当前配置下的小规模基线，不能外推多节点水平扩展或
  千万用户量级；峰值内存仅覆盖这三类查询，不含全量八类工作负载。
- 工作负载是 insert-only，单调性只在该前提下成立；更新/删除场景由 erasure
  与 retention 的专项测试覆盖。
- 本证据不改变 514/728 的失败记录；高基数长尾身份/字段分布下的稳态容量、
  跨故障域多副本拓扑仍需独立专项。
