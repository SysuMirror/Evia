# Disposable backend integration dependencies

This profile runs real Apache Kafka, ClickHouse and Redis for synthetic backend
integration tests. It is one local broker/controller, one ClickHouse node and one
Redis process. It does not establish production availability, disaster recovery
or capacity. Stateful Flink processing remains a separate, unimplemented phase.

Use Docker Engine, Compose 2.23.1 or newer (inline configuration support), Python
3.12 or newer and the Go toolchain from the [development runbook](development.md).
Run commands from the repository root. Reserve loopback ports 19092, 18123, 19000
and 16379. The profile does not start PostgreSQL or use ports 55432, 8080 or 5173.

## Start only the dependencies needed

Generate a private configuration file outside the checkout. The helper refuses
to replace an existing file or create credentials inside the repository, uses
mode 0600 and prints no values:

```bash
./deploy/dev-env init /tmp/evia-pipeline.env
./deploy/dev-env up /tmp/evia-pipeline.env
./deploy/dev-env check /tmp/evia-pipeline.env
./deploy/dev-env status /tmp/evia-pipeline.env
```

The Compose project is `evia-pipeline-dev`; explicit service selection keeps an
existing development PostgreSQL untouched. `up` waits for health and fails if a
dependency cannot start. `check` verifies Kafka broker metadata, authenticated
ClickHouse SQL and authenticated Redis PING. For a smaller dependency set, pass
service names to `up`, `check`, `status` or `down`:

```bash
./deploy/dev-env up /tmp/evia-pipeline.env kafka clickhouse
./deploy/dev-env check /tmp/evia-pipeline.env clickhouse
./deploy/dev-env up /tmp/evia-pipeline.env redis
```

Do not run `docker compose config` without `--quiet` against the private file:
expanded configuration contains credentials. Do not upload that file, container
environment inspection output or unreviewed dependency diagnostics. Application
and dependency passwords in this profile are generated only for synthetic tests.

| Dependency | Host endpoint | Test configuration | Authentication |
| --- | --- | --- | --- |
| Kafka | `127.0.0.1:19092` | `EVIA_TEST_KAFKA_BROKERS` | PLAINTEXT; isolated local tests only |
| ClickHouse HTTP | `http://127.0.0.1:18123` | `EVIA_TEST_CLICKHOUSE_URL`, `EVIA_TEST_CLICKHOUSE_USERNAME`, `EVIA_TEST_CLICKHOUSE_PASSWORD` | Generated password, user `evia` |
| ClickHouse native | `127.0.0.1:19000` | Available for operator inspection | Same generated user/password |
| Redis | `127.0.0.1:16379` | `EVIA_TEST_REDIS_URL` | `redis://default:GENERATED_PASSWORD@127.0.0.1:16379/0` |

The generated file also supplies a random `EVIA_DEV_KAFKA_CLUSTER_ID` and
`EVIA_DEV_REDIS_PASSWORD`. Its `EVIA_POSTGRES_PASSWORD` exists only because
Compose resolves the PostgreSQL service definition; it does not configure or
alter an existing PostgreSQL instance. These test variables are not a complete
application runtime configuration.

Kafka advertises `kafka:9092` inside this Compose network and
`127.0.0.1:19092` to host clients. It disables automatic topic creation, so tests
must explicitly create their own uniquely named topics. The local replication
factor and minimum in-sync replicas are both one; unclean leader election is
disabled. A single broker cannot validate the intended production replication
factor of three, minimum in-sync replicas of two or broker-loss durability.
Successful local acknowledgements do not prove those guarantees.

ClickHouse uses a plain single-node MergeTree topology, so no Keeper is needed.
The synthetic administrator can create and drop isolated test databases. The
profile creates no application tables: tests or an explicit administrative DDL
step must apply the matching scripts in `deploy/clickhouse`. Service startup
never applies application migrations. Use database names generated by the test
helper; drop only databases that the test created.

Redis uses a generated password, a 64 MiB data limit and `noeviction`. It disables
snapshots and append-only persistence because this profile verifies transient
quota behavior. Tests must use unique key prefixes and delete only their own
keys, without `FLUSHDB` or `FLUSHALL`.

## Run targeted real tests

Inject the private settings into a command without printing them or sourcing
shell code:

```bash
./deploy/dev-env run /tmp/evia-pipeline.env -- go -C backend test -race -tags=integration ./internal/pipeline -count=1
./deploy/dev-env run /tmp/evia-pipeline.env -- make query-test
./deploy/dev-env run /tmp/evia-pipeline.env -- make budget-test
```

These commands select the Kafka-to-ClickHouse, query and Redis quota packages
respectively. The
existence of a dependency profile or test command does not establish that an
in-progress module has passed; consult PROGRESS.md for actual results. Explicit
integration tests must fail when their required configuration is missing or
their dependency is unavailable. Unit tests and mocked collaborators do not
substitute for these checks.

`make pipeline-test` selects the same pipeline integration package and fails
before testing if its Kafka/ClickHouse configuration is missing. Its CI matrix
job starts only Kafka and ClickHouse, uses fresh private credentials and runs the
same race-enabled target. A workflow definition does not prove a hosted CI run
passed; record the actual run with the module evidence.

`make budget-test` selects `./internal/platform/budget` and `./internal/ingestion`
with the integration tag and race detector, and requires `EVIA_TEST_REDIS_URL`.
Its independent CI matrix job starts only Redis and verifies the atomic budget
against that real service, including the full Collector admission chain. Redis
Cluster and Sentinel baseline tests skip with a stated reason when their topology
variables are absent; the HA drills supply them and run those tests explicitly.

`make query-test` selects `./internal/analysis` with the integration tag and race
detector, requires the ClickHouse URL/username/password and creates isolated
databases. Its independent CI matrix job starts only ClickHouse. The tests
exercise real query cancellation through `system.processes` as well as result
semantics; no Kafka or PostgreSQL service is substituted for this boundary.

## Resource limits and cleanup

Compose requests one CPU and 1536 MiB RAM for Kafka, with a 512 MiB data tmpfs. Topic
retention is bounded at 64 MiB per partition and one hour. ClickHouse requests
two CPUs and 2048 MiB RAM, with a 1536 MiB server memory budget, a 512 MiB data
tmpfs and a 64 MiB log tmpfs. Its caches and background pools are reduced and
profiling system logs disabled for this local test workload. Redis requests
half a CPU and 128 MiB RAM, with a 16 MiB data tmpfs. Container stdout logs rotate
at 20 MiB total per Kafka/ClickHouse service and 10 MiB for Redis. All tmpfs
allocations count against RAM; reaching an enforced limit is a real test failure.
Image layers remain in Docker's image cache.

Per-container CPU/RAM/PID enforcement requires a Docker daemon with working
cgroup support. `deploy/dev-env up` checks CPU/RAM support and warns when those
limits cannot be enforced. The managed local daemon used for initial verification
reported rootless mode, cgroup driver `none`, `MemoryLimit=false` and
`CPUCfsQuota=false`; its containers inherited the outer executor's 16 GiB RAM and
four-CPU quota. Its Compose limits are recorded but not enforced. Application
memory limits and tmpfs sizes remain configured. Do not treat this environment
as evidence that per-container limits work, or restart a shared daemon to change
its configuration. CI and other development hosts must check their own daemon.

Data is disposable: stopping/recreating these containers can lose all test data.
Coordinate with anyone currently running integrations before changing Compose
configuration or recreating a dependency. To stop and remove only these service
containers, preserving the shared PostgreSQL and all unrelated containers:

```bash
./deploy/dev-env down /tmp/evia-pipeline.env
```

Keep the private configuration while reusing the same dependency containers;
changing its password does not change credentials in an already running
container. Remove the private file only after stopping its services and when it
is no longer needed. The helper does not run daemon-wide cleanup.

## Image provenance

Versioned images are pinned to multi-platform manifest digests in
`deploy/compose.dev.yaml`. These official project registries supplied the tags
and digests, and Docker pulls verified the same digests:

- [Apache Kafka 4.4.0 image](https://hub.docker.com/r/apache/kafka/tags?name=4.4.0)
  and [upstream version declaration](https://github.com/apache/kafka/blob/4.4.0/gradle.properties).
- [ClickHouse 26.8.36.3 image](https://hub.docker.com/r/clickhouse/clickhouse-server/tags?name=26.8.36.3).
  An authenticated `SELECT version()` verifies the running official build.
- [Redis 8.10.3 Alpine image](https://hub.docker.com/_/redis/tags?name=8.10.3-alpine)
  and [upstream version declaration](https://github.com/redis/redis/blob/8.10.3/src/version.h).

Review upstream release/security notes before changing either a version or its
digest. This minimal local topology is not a production deployment template.
