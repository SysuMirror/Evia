# 大范围属性查询与并发容量：缺口分析与改进方案

> **状态：A 类修复已交付（2026-11-20，[修复验证](../verification/query-capacity-fix-2026-11-20.md)：同数据集 728/728 全绿，属性类 182→0、并发类 20→0）；B 类并发拒绝随剪枝一并清零，统一内存准入设计暂无独立需求。** 复现基线见[复现记录](../verification/query-capacity-repro-2026-11-20.md)。 本文件整理 514/728 百万矩阵失败的证据归类、根因假设与分层改进方案。文中没有任何一项已经作为容量修复交付；所有假设在复现环境验证前不得当作结论，所有方案在对应验收通过前不得计入能力清单。数字一律引自既有验证记录，未新增任何测量。

## 1. 现状与证据基线

权威来源是[百万查询报告](../verification/query-capacity-2026-11-09.md)（2026-11-09，最终后端 `9dfa020`）：1,000,000 条唯一事件 + 100,000 条原样重放 + 100,000 个 UID，主机 5 CPU / 约 17.6 GiB 内存，`GOMAXPROCS=2`、两个查询工作任务、每查询最多 2 个 ClickHouse 执行线程，服务端总内存上限 3 GiB；单查询预算为 2,000,000 行、256 MiB 扫描、512 MiB 内存、30 秒执行。八类查询各 91 样本（首次观测 + 并发 1/4/8 各 30 重复），共 728 次，最终后端通过 **514 / 728**。

已经交付且不重复实现的存储优化（报告同轮）：紧凑胜出排序列（ClickHouse 迁移 004）、原始 UID/匿名标识候选投影（005）、固定授权范围聚合简化、数值属性 `JSONType` Double 判断修复。属性列裁剪原型因 `1e2`、`1.00`、长小数、数组负零等词法不等价而撤回，教训已固化在[属性读取设计](property-read-layout.md)。

属性读取的后续主线（token Map 停用、专用热键列方案）在 property-read-layout.md 中已推进到：纯 Go 派生器、迁移 006–009、默认关闭的写入器与读取器接线、视图/迁移生成工具，以及 G1（token 列探针）、G2（视图层）、G3（百万行物理矩阵）三轮物理门全部通过（2026-11-12/13）。**停在**：首个生产热键目录尚未批准，槽位列迁移未提交，backfill 未演练，读取路径未切换——因此文档路径仍是唯一生产读取路径，514/728 矩阵未复测。

另有两份与本缺口直接相关的既有探针（见[压测手册](../runbooks/benchmark.md)）：多租户查询内存隔离探针证明单查询硬封顶演绎上界（N 并发 ≤ N×512 MiB）、有界查询在嘈杂邻居波里 100% 存活；查询护栏完整性探针把 241（内存）、158/396（读取/结果行与字节）、159（超时）、394（取消）的确定性触发钉死。它们是方案层验收的基础设施，不是容量结论。

## 2. 缺口分类

214 次失败全部经 API 以 `QUERY_COST_EXCEEDED` 返回（`analysis/clickhouse.go` 把 `LIMIT_EXCEEDED`/`TOO_MANY_*`/`MEMORY_LIMIT` 类数据库异常翻译为该码），没有截短的成功结果。按工作负载分成两类：

| 类别 | 规模（成功/尝试） | 表现 | 伴随的数据库层证据 |
| --- | --- | --- | --- |
| A. 属性类 | 属性分组 **0/91**、数值属性筛选 **0/91**，合计 182 次失败 | 并发 1 即全部失败，与并发无关 | 最终窗口捕获 165 次扫描字节上限错误（Code 307）为主 |
| B. 统计类并发拒绝 | 事件计数 83/91、精确 UID 74/91、小时分桶 84/91，合计 32 次失败 | 仅出现在并发 4/8 档 | 捕获 41 次服务端总内存错误（Code 241） |
| 对照 | 指定 UID 筛选、单 UID 行为链、单 UID 有序漏斗 273/273 | 全通过（身份投影收益） | — |

两点必须如实保留：其一，41 + 165 = 206 个数据库错误与 214 次 API 失败**不是一一对应**（报告明言查询日志不完整、未逐任务关联），错误类别归属是强倾向而非映射；其二，单工作任务复验（27/27，并发 8，p95 30.9/42.0/31.0 秒）证明统计类失败对工作并发敏感，但排队时延随之上升，是配置复验不是新矩阵。

## 3. 根因假设（均待复现验证）

- **H1（高置信）：类 A 源于整文档属性读取。** 任何属性字段都会让趋势胜出元组携带 `properties_json` 与 `property_tokens`（`trend_facts.go` 的 `WalkFields` 分支），`planner.field` 用 JSON 函数在文档上解析（词法等价约束使之无法用数据库侧抽取器替代）。百万宽文档行的扫描字节直接顶穿 256 MiB 单查询上限。G3 专用列矩阵的对照数字（数值筛选读取 2674 MiB → 4.7–7.6 MiB、峰值内存 57.2 MiB → 2.3 MiB）与 307 错误形态互相印证。【需基准复现验证一对一归属】
- **H2（中置信）：类 B 源于服务端总内存，而非单查询预算。** 两个工作任务各跑一个近上限查询的演绎上界约 1 GiB，低于 3 GiB 服务端上限，但 241 错误确实发生；未入账的聚合状态、后台合并、mark 缓存与多查询交叠是候选构成，报告明确「不能用单查询仍低于 512 MiB 解释为资源足够」。【需复现时用 `system.query_log` + `system.metrics` 采样定位缺口】
- **H3（中置信）：精确 UID 与小时分桶的内存主体是 `uniqExact` 集合与聚合状态。** 十万 UID 基数下集合本身有限，并发交叠才是压力来源；与 H2 同源。【需复现验证】
- 不单列超时类：报告捕获的错误里未把 159（执行超时）列为独立失败类别，并发 8 成功样本 p95（20–30 秒）接近 30 秒上限但不构成已证实的失败机制，不预设有超时失败类。

## 4. 改进方案（分层）

### 4a. 无语义损失的机械优化

1. **专用热键列生产化闭环（类 A 的主路径，前置是决策不是代码）。** 按 property-read-layout.md 既定阶段推进：批准首个生产目录（≤8 槽位）→ `evia-catalog-migration` 生成槽位迁移并提交 `deploy/clickhouse` → 有界 backfill 演练（显式批准后才动）→ 读取路径 go/no-go → 复测 728 矩阵。全部接线已存在且默认关闭，此路径不新增语义风险；词法等价由既有 18 形态矩阵、混合胜者与边界用例守护。
2. **工作并发作为受控策略而非隐式默认。** 单工作任务复验已证明方向；把「重扫描类查询的并发压制」（例如按扫描类别准入或可配置的工作并发档位）作为显式运营策略记录，默认双任务配置与其失败基线一并保留，不互相覆盖。
3. **类 B 复现时的内存记账采集。** 在 `system.query_log` 既有 `read_rows`/`read_bytes`/`memory_usage`/`query_duration_ms` 归档之上，补服务端 `system.metrics`/后台合并活动采样，先把 H2 的缺口定住，再决定是否需要跨实例统一内存准入（该能力报告明言未实现，属独立设计）。

### 4b. 需语义论证的优化（默认不做，列出论证条件）

4. **字符串分组内存的进一步削减**：G3 后字符串分组峰值约 135 MiB（来自 180.3 MiB），若并发 8 下仍顶穿服务端总内存，候选是字典/LowCardinality 化分组键，必须先证明排序、去重与缺失/null 语义逐字节等价，复用既有等价性矩阵方法。
5. **有界重试的失败语义**：对 241 类服务端总内存拒绝做单次有界退避重试，会把部分失败转化为时延；改变失败报告语义，需产品签收后才可进入实现。

### 4c. 需要产品决策的（本计划不推进）

6. 放宽单查询 256 MiB 扫描或 3 GiB 服务端内存——与「不靠放宽预算换通过」的既有验收原则冲突，只能作为独立容量决策连同成本模型另议。
7. 高并发下自动降级近似 UV/分位数——当前近似是显式 opt-in，自动降级改变结果语义，仅列为产品选项。

## 5. 验收条件

任何方案宣称完成，须同时满足：

- **同条件复测**：同一百万数据、资源、查询集合与并发（`benchmark.py queries --samples 30 --concurrency 1,4,8`），不改任何预算常量；按工作负载分别报告成功数变化，失败与排队照实保留，不摘成功样本。
- **语义对照**：属性读取切换沿用 18 形态双库等价矩阵 + 混合胜者 + 词法边界用例全部字节一致；统计类改动前后计数/UV/分桶结果逐字节一致。
- **配套证据**：多租户隔离与查询护栏探针在改动后重跑通过；混合读写演练（`tooling/ha/mixed_workload_drill.py`）不回归。
- **归档**：二进制哈希、配置、起止时间、`system.query_log` 明细与失败分类进验证记录，更新 PROGRESS 与功能覆盖清单时区分「物理可行」与「容量签收」。

## 6. 复现环境清单（引用既有手册，全部命令见[压测手册](../runbooks/benchmark.md)）

- `compose.benchmark.yaml` 独立 Compose 项目（磁盘卷 ClickHouse，避开 512 MiB tmpfs），装载前 ≥8 GiB 可用磁盘；宿主机资源对齐报告量级（约 5 CPU / 17.6 GiB 内存档）。
- `tooling/benchmark/runtime.py` init/prepare → `benchmark.py prepare --uid-cardinality 100000` → `evia-bench --events 1000000 --batch-size 50 --concurrency 16 --replay-percent 10` → `benchmark.py queries --samples 30 --concurrency 1,4,8 --drain-timeout 900`。
- 记录 `EVIA_QUERY_WORKERS` 实际值与共享同一 ClickHouse 的工作进程总数；采样器 `observe.py --duration 1800 --interval 5` 伴随全程。
- 属性读取闭环额外需要：已批准的生产目录 JSON、生成的槽位迁移、backfill 演练盘（按 retention 演练的 9 倍临时磁盘余量原则另行评估列重写形态）。
- **下一步执行者**：批准生产目录后的容量切片负责人；本备忘录的 H1–H3 归属验证可与目录审批并行，复用同一环境先跑一次带 `system.query_log`/`system.metrics` 采样的基线。

## 7. 风险与开放问题

1. **生产目录内容待定**：8 个槽位放哪些 `(event_key, schema_version, property_key)` 需要按论坛业务事件模式评审；示例目录明确非生产。目录错误只会损失性能不会损失正确性（读取器按命中门控），但会浪费列与写入成本。
2. **241 记账缺口**（H2）：单查询预算演绎上界与观测到的服务端总内存错误之间的构成未定位，是类 B 一切方案的前置未知数。
3. **backfill 形态未定**：现有 9 倍余量模型针对 retention mutation 重写；属性槽位列的历史物化是否需要同量级余量、边界月份与多 part 形态如何迁移到该场景，需独立探针。
4. **字符串分组并发余量**：G3 单客户端 135 MiB 峰值在并发 8 下的服务端叠加未测量。
5. **多副本统一内存准入**：跨实例共享数据库的准入设计（Redis 令牌还是引擎侧协调）完全未起步，属高可用工作包交界。
6. 本文件写作时未复跑任何基准；所有「预计消除类 A」的说法都以 G3 物理门证据为依据，最终以 728 矩阵复测为准。
