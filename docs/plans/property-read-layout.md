# Property read layout: deferred design

The compact winner columns and identity projections improve count and identity queries. Property filters, grouping and metrics still read the original `properties_json` String. No property-column migration or reader switch is delivered. Existing scan, memory and timeout budgets remain in force.

An isolated ClickHouse 26.8.36.3 prototype encoded decoded top-level UTF-8 keys as `p_` plus uppercase hexadecimal and stored each value as a String in native JSON. This avoids dotted-key collisions and Dynamic numeric inference; dedicated and shared-overflow paths can be selected individually. However, constructing those Strings with `JSONExtractKeysAndValuesRaw` does **not** preserve the original value tokens:

| Original value | Extracted raw text | Consequence after reconstruction |
| --- | --- | --- |
| `1e2` | `100` | `JSONType` changes from `Double` to `Int64` |
| `1.00` | `1` | Floating-point token becomes an integer token |
| `0.1234567890123456789` | `0.12345678901234568` | Decimal text is rounded |
| `[-0.0]` | `[-0]` | `Array(String)` extraction changes from `["-0"]` to `["0"]` |

`JSON_QUERY` also normalizes these values. Dynamic map extraction additionally rounded the integer `9007199254740993`. `simpleJSONExtractRaw` preserves lexical tokens but does not safely distinguish arbitrary escaped keys and nested matching keys. These methods cannot establish a lossless generic property read path. The prototype was removed; its read savings are not production capacity evidence.

The investigation also found an independent correctness bug: ClickHouse's `JSONType` reports floating-point values as `Double`, whereas the numeric field guard checked the SQL name `Float64`. The delivered guard correction includes decimal and exponent values in existing numeric metrics, comparisons and grouping, while still excluding missing, null, string, boolean, array and object values. This fix continues to use the original property document and does not change array extraction or introduce a new storage layout.

A future design must preserve each top-level value using a verified lossless extractor. One candidate is to derive an encoded map of per-property `json.RawMessage` tokens alongside the original document in the existing writer and commit both in the **same raw-table insert**. The original document remains authoritative; the map is a derived read layout. This requires an explicit layout version, strict decoded-key uniqueness and exact handling of missing, null, arrays, objects, integer precision, decimal/exponent tokens and signed zero. It must not add a second independently committed fact write.

Old writers and old parts require an explicit compatibility and readiness plan before switching readers. Historical backfill must use a verified lossless parser, rewrite bounded inspected partitions and retain the original documents. A successful ALTER acknowledgement or schema version alone does not prove every relevant part is materialized. Readers must retain the original path until the required layout is present and verified for the selected data; rollback must remain possible. A database-side extractor is another option only after lexical and query-result equivalence is demonstrated on the same edge cases.

One compatibility option to verify is a server-computed legacy-document column: layout version zero retains the original document, while a new writer atomically supplies version one and the losslessly derived values, making that legacy column empty. A reader would choose the legacy document or reconstructed requested values from the **same winning tuple**. This could allow old writers and unmaterialized parts to remain correct without requiring new parts to read the full original document. It still needs physical-read verification, omitted-field profile tests and constraints on the writer-owned layout marker. It is a design option, not an implemented fallback or permission to replace an active partition while ingestion continues.

Any future native JSON layout needs a finite per-part dynamic-path limit, correct shared-storage fallback and measurements on realistic key distributions. Validate conflicting winners, source and version boundaries, legacy and new writers, missing/null/false/zero, unsupported shapes and precision before measuring complete production queries under the existing budgets. Storage duplication, insert CPU, merge cost and bounded backfill cost must be included in that assessment.

## Landed foundation: lossless Go token deriver

The first building block now exists as `backend/internal/propertylayout`. It is a pure, side-effect-free package with no writer or reader call sites yet, so it cannot change any stored or served data:

- `EncodeKey`/`DecodeKey` map a decoded top-level key to `p_` plus uppercase hexadecimal of its UTF-8 bytes and back. The transform is reversible and collision-free for dotted, spaced and non-ASCII keys.
- `DeriveMap` parses a canonical properties object into `map[encodedKey]json.RawMessage`. Values stay as their exact input tokens because `json.RawMessage` is never re-serialized through a numeric Go type; a streaming token pass first rejects duplicate decoded keys, non-objects, trailing data and malformed JSON, and the property cap of 50 is enforced.
- Unit tests pin the lexical edge cases from the table above (`1e2`, `1.00`, the long decimal, `-0.0`, the integer beyond the safe range) plus null/false/zero, arrays, nested objects, empty objects, token copy isolation and over-limit documents.

The remaining work, still gated behind real ClickHouse physical-read verification, is: add an explicit layout version and derived columns in a migration, have the writer commit the derived map atomically with the authoritative document in the same raw-table insert, build a reader that chooses the original document or reconstructed values from the same winning tuple while retaining fallback for old writers and unmaterialized parts, and then run a bounded backfill and the full query matrix under the existing budgets. The deriver alone is not a capacity claim.

## Landed storage: version 006 columns and atomic writer layout

The next two building blocks now exist, still without any reader switch:

- Migration `deploy/clickhouse/006_property_layout.sql` adds `property_layout_version UInt8 DEFAULT 0` and `property_tokens Map(String, String) DEFAULT map()` to `event_facts_raw`. The map keys are the `p_`-prefixed hexadecimal identifiers and the values are the exact JSON token texts. Sort and partition keys, historical parts and the `event_facts` view tuple are intentionally untouched, so applying the migration cannot change a served query result. Legacy parts and writers that omit the fields read version 0 and an empty map through type defaults.
- The fact writer now calls `propertylayout.DeriveMap` on the normalized document inside `rowFor` and commits `property_layout_version = 1` together with `property_tokens` in the same JSONEachRow insert as the authoritative `properties_json`; there is no second fact write. A derivation error fails the insert closed. The existing `input_format_skip_unknown_fields=0` profile makes a database that has not applied 006 reject the new writer instead of silently dropping the layout, and an integration test pins that fail-closed ordering between migrations 003 and 006.
- Integration evidence on ClickHouse 26.8.36.3 pins the stored map tokens byte-for-byte against the Go deriver for `1e2`, `1.00`, the long decimal, `-0.0`, `0`, `false`, strings and arrays inside the ingestion contract, confirms that an empty properties object legitimately stores version 1 with an empty map, and confirms a simulated pre-006 writer stores version 0 with an empty map while the view keeps serving its authoritative document. This is storage correctness evidence only; it is not a scan-byte or capacity claim.

## Landed view: version 007 exposes the layout on the deduplicated tuple

Migration `deploy/clickhouse/007_property_layout_view.sql` recreates `event_facts` with the original 26 argMin tuple slots unchanged and appends `property_layout_version` as fact.27 and `property_tokens` as fact.28. The winner weight is unchanged, so the layout always describes the same winning row as the exposed `properties_json`; legacy parts contribute the version-0/empty-map defaults. An isolated probe and an integration test both confirm that `argMin` carries the `Map(String, String)` coherently through the tuple, including the exact lexical tokens, and a view test pins two mixed-replay identities: a version-1 winner exposes its tokens while a version-0 winner keeps an empty map even when the losing replay carries version 1. No reader selects the new columns yet, so served results are unchanged; the full analysis and pipeline integration suites stay green.

## Landed reader: same-tuple token selection with document fallback

The reader switch now exists in `planner.field` and the trend winner subquery:

- Every property expression binds the encoded key (`propertylayout.EncodeKey`, moved to the shared `internal/propertylayout` kernel so neither side depends on the other's subtree) as a parameter. A row-level gate `property_layout_version=1 AND mapContains(property_tokens, {encoded})` chooses between a synthetic one-field document built from the exact token and the authoritative `properties_json`; the JSON key is the fixed server literal `f` on the layout path and the bound user key on the fallback path. Because each token is byte-identical to the original document substring, `JSONType`/`JSONExtract*` results are identical by construction, and any version other than 1, old writer or unmaterialized part reads the document.
- The trend winner subquery appends the two layout columns to its argMin tuple only when a property field is present, so the selection stays inside the same winning row; view-backed queries receive them from the version 007 view.
- Evidence: a unit test pins the gated SQL shape and the bound-parameter rule; an integration test runs an 18-shape matrix (numeric aggregates, numeric/string/boolean/array filters, presence, three groupings and a view-backed events query) against two isolated databases holding identical logical data as version-0 rows and version-1 token rows, with byte-identical result rows; a mixed-winner test pins per-row fallback when version-0 and version-1 replays compete for the same identity. The full analysis and pipeline suites remain green. This is query-correctness evidence, not yet a physical-read or capacity measurement.

## Physical-read gate: failed, rollout parked

The controlled measurement in [property-layout-reads-2026-11-10](../verification/property-layout-reads-2026-11-10.md) ran the exact reader expressions above against 200,000 wide-document rows on ClickHouse 26.8.36.3. The `Map(String, String)` layout did not pass the gate that this plan requires:

- Version-1 token queries read about 27% more bytes, selected 80% more marks and needed about 183% more peak memory than the document path, while returning identical rows. MergeTree stores a Map as parallel key/value array streams and a point lookup still reads the whole granule of those streams; the single highly compressible document column (~31x in that profile) is cheaper to query despite being larger uncompressed.
- Because all existing data is version 0, the most consequential number is the fallback cost: the gated reader on version-0 rows stays flat on read bytes (+0.4%) but raises peak memory by about 71% and latency by about 38%, which directly worsens the 512 MiB memory budget behind the original failures. View-level aggregation with the Map inside the argMin tuple also exceeded the container temporary-disk quota.

The decision is to keep the landed code (deriver, migrations 006/007, writer and reader with their tests) but not to backfill or roll the layout out as a production read optimization, and not to claim any capacity improvement. The schema defaults keep version-0 behavior unchanged. Any successor layout (a bounded set of dedicated hot-key columns, a JSON-subcolumn design with the same lexical-equivalence harness, or a re-test on realistic low-compressibility data) must pass the same dataset and metric gate first; the version-0 fallback memory overhead is profile-independent and must be eliminated or made opt-in before another reader attempt.

## Successor gate: dedicated hot-key columns pass the physical-read probe

The first successor candidate named above now has physical-read evidence, recorded in [property-layout-dedicated-columns-2026-11-12](../verification/property-layout-dedicated-columns-2026-11-12.md). The isolated harness `tooling/benchmark/property_layout_probe.py` loads identical 100,000-row wide-document data into three layouts (document baseline, the parked token Map, and a table materializing two hot keys as typed columns) and applies the same metric gate: continuous read-byte and memory metrics within 2% of baseline, SelectedMarks within an absolute two-granule allowance and a 1.10 ratio cap.

- The dedicated columns pass every metric in both the numeric filter and the string grouping workload. Numeric filtering reads 0.3% of the baseline bytes at 0.5% of its peak memory; string grouping reads 3.7% of the bytes at 52.6% of the memory; marks move 27 to 28, a single-granule alignment delta inside the explicit allowance. The parked Map fails the same probe again (2.185x marks in both workloads, 13.86x peak memory on the numeric filter), independently reproducing the 2026-11-10 decision on a fresh harness.
- This is gate evidence only. The probe is tooling, not production code: no migration, writer, reader or stored data changes, and the 514/728 capacity matrix is not reopened. A production design still needs a hot-key identification mechanism with a bounded column count and schema-evolution rules, same-insert atomic materialization alongside the authoritative document, a reader with version-0 fallback, a bounded backfill plan, and a lexical-equivalence story for typed columns (numeric columns cannot preserve tokens such as `1e2` or `-0.0`). The full query matrix under the 512 MiB budget must pass before any reader switch; until then the document path remains the only production read path.

## Productionization design for dedicated columns (proposal, not approved)

The 2026-11-12 probe gives the bounded dedicated-column candidate its physical-read qualification, but no production code may change until this design is reviewed and its open decisions are signed off. The design is anchored to the seams that already exist: the Go deriver in `internal/propertylayout`, the single-insert writer in `internal/pipeline/clickhouse.go` (`rowFor` / `factRow`), the gated reader in `internal/analysis/planner.go` (`field`) with its selective winner-tuple append in `trend_facts.go`, and the additive-migration pattern of 006/007.

### Hard constraints inherited from the landed layout work

1. `properties_json` stays the authoritative payload on every row; every derived column is a read accelerator, never a source of truth.
2. Derived values must stay lexically lossless (`1e2`, `1.00`, `-0.0`, integers beyond the safe range keep their exact token). Any typed-column exception needs an explicit, narrowed contract, not a silent relaxation.
3. Derived columns commit in the same raw-table insert as their document; a derivation error fails the insert closed. No second fact write.
4. Old parts and old writers must keep serving correct results through structural defaults; rollback to the document path must always remain possible.
5. No backfill, no reader switch and no capacity claim until the re-gates below pass on the real 512 MiB environment. The standing prohibition on property-layout backfill is only lifted by an explicit go/no-go decision after stage 2.

### D1. Hot-key catalog: how columns are chosen

The probe materialized two keys out of twenty-five. A production table cannot grow a column per observed key, so hot keys need a bounded, reviewable catalog keyed by the same identity the planner already binds: `(event_key, schema_version, property_key)` plus the catalog-resolved type.

- **Proposal (v1): static operator catalog.** A versioned catalog with a hard cap of eight slots (16% of the 50-property ingestion limit), changed only through reviewed configuration and an additive migration. Predictable column set, no feedback-driven schema churn, auditable in the same governance flow as retention and quota changes.
- Rejected for v1: automatic promotion from query frequency. Column churn, cold-start oscillation and merge pressure are unmeasured; it can be designed later as an extension that proposes catalog revisions for human approval, never as self-service ALTERs.
- A key removed from the catalog stops being materialized for new rows but its column stays readable; physical column removal is a separate, later migration validated in isolation.

### D2. Column typing and the lexical-fidelity fork (decision required)

- **Option A — String token columns (recommended for v1, now evidence-backed).** Each slot stores the exact JSON token text, exactly as `property_tokens` values do today but in an independent column stream. The reader reuses the proven synthetic one-field document (`concat('{"f":', col, '}')`), so every `JSONType`/`JSONExtract*` behavior and lexical edge case stays identical by construction. This respects constraint 2 without exemptions. The G1 sub-gate (see [the verification record](../verification/property-layout-dedicated-columns-2026-11-12.md)) now measures this exact shape: it passes both workloads, with numeric filtering at 0.17% of baseline read bytes and 8.11% of peak memory, and string grouping effectively tied with the raw String column (52.68% vs 52.62% memory). Per-row JSON parsing costs about fifteen times the typed column's memory in absolute terms (2.39 MiB vs 0.16 MiB), still negligible against the 512 MiB budget.
- Option B — typed columns (`Int64`/`Float64`/`String`). Fastest in the probe, but numeric typed columns cannot preserve `1e2`, `1.00`, `-0.0` or oversized integers, conflicting with constraint 2. It would require narrowing the contract to validated integer-domain catalog entries and keeping the document authoritative for any value extraction/display, with a per-key exemption recorded in the catalog. Not acceptable as a default.
- Option C — dual columns (lossless String token plus typed shadow). Doubles write and storage for shadowed keys. The G1 evidence gives no reason to adopt it in the measured profile: Option A already passes with an absolute 2.2 MiB memory difference, so a shadow column would add complexity without a budget-driven need.
- Decision after G1: proceed with Option A. Typed columns (Option B) and dual columns (Option C) stay unimplemented; any future exemption requires a failing G3 measurement, not a speculative optimization.

### D3. Schema, markers and evolution

- Migration 008 adds, per catalog slot, one `String DEFAULT ''` column named with `propertylayout.EncodeKey` (the same `p_`-hex identifiers as the map, so a key maps to exactly one physical name and cannot collide with fixed columns). `ADD COLUMN` is metadata-only; historical parts read the default and need no rewrite, matching the 006 precedent.
- A row-level marker `dedicated_layout_version UInt8 DEFAULT 0` records the catalog revision at write time. The reader gate is marker **and** non-empty token, never the column alone: an empty string means "not materialized on this row" (old part, pre-catalog key), while a legitimate empty-string property still stores the two-byte token `""`.
- Migration 009 recreates `event_facts` appending the marker and slots as fact.29 onward; the existing 28 slots, winner weight and ordering are untouched, so applying it alone cannot change a served result, exactly as 007 did for the map.
- Column deprecation is two-phase (stop writes with reader fallback verified, then a later removal migration); no slot is reused for a different property key.
- Implementation note (2026-11-13): migration 008 landed as marker-only. Because no production hot-key catalog has been approved, inventing slot columns now would bake synthetic keys into the schema; the first slot-column migration is therefore deferred to stage 3b and must name the exact encoded columns of the first approved catalog.

### D4. Writer changes

`factRow` gains the bounded slot fields plus the marker. `rowFor` populates them from the **same** `DeriveMap` result it already computes — no second parse, no database-side extractor — copying tokens verbatim. Keys outside the catalog leave their slot empty; the marker still records the catalog revision so readers can distinguish "absent by catalog" from "legacy row". A derivation or encoding error keeps failing the insert closed, and the existing `input_format_skip_unknown_fields=0` ordering makes a not-yet-migrated database reject the new writer instead of silently dropping columns.

### D5. Reader changes and fallback chain

`planner.field` gains an outer branch ahead of the parked map branch:

1. catalog hit for `(event_key, schema_version, key)` **and** `dedicated_layout_version` gate on the row → synthetic document from the dedicated String token;
2. else the existing version-1 map gate;
3. else the authoritative `properties_json` document.

All three branches keep the user key as a bound parameter and return the same `fieldSQL` shape. `trend_facts.go` appends dedicated columns to the winner tuple only when a walked property field resolves to a catalog slot, reusing the current selective-append pattern; view-backed queries receive them through the 009 tuple. The existing 18-shape equivalence matrix is extended to a third layout identity with byte-identical result rows, plus a mixed-marker winner test in the style of the current version-0/version-1 test.

### D6. Backfill (proposal only; remains prohibited until explicitly approved)

If re-gates justify it: a Go-driven, partition-bounded rewrite using the verified deriver — never a database-side JSON extractor — rewriting inspected month partitions while retaining the original documents, with per-batch row-count and token hash verification and a rollback path. The archive/backfill worker pattern in `internal/backfilling` is the operational reference. No ALTER acknowledgement is treated as materialization proof; readiness is per-part verification, mirroring the discipline already written into this plan.

### D7. Re-gates required before any reader switch

- **G1 — token-column sub-gate (completed 2026-11-12).** `property_layout_probe.py` now includes the String-token `dedicated_token` layout; it passes both workloads under the same 2% / mark tolerances and decides D2 in favor of Option A, with two byte-identical independent runs. Decimal/exponent token parsing remains deferred to the G3 equivalence matrix.
- **G2 — view-layer gate (completed 2026-11-13).** `property_layout_view_probe.py` builds an argMin view per layout and runs a trend-style aggregation, recording query status alongside physical metrics. On the 512 MiB tmpfs the map tuple fails with ClickHouse error 243 (cannot reserve ~724 MB temporary space), reproducing the parked layout's view-path failure; both dedicated and dedicated-token tuples succeed at ~3.9% more read bytes and ~6.3% more peak memory than the document-only tuple (about 378 MB vs 356 MB), with identical counts. This is evidence of feasibility, not capacity sign-off: see the verification record for the G3 million-row caveat.
- **G3 — million-row matrix (physical gate passed on host-disk CH, 2026-11-13).** On the 4 GiB host-volume benchmark ClickHouse, four 1,000,000-row wide tables ran the count/unique/numeric-filter/string-group matrix at concurrency 4 (48 queries, 3 repeats): all succeeded within the 512 MiB per-query budget with byte-equivalent cross-layout results. Numeric-filter peak memory fell 57.2 MiB→0.2 MiB (typed) / 2.3 MiB (token) and read bytes 2674 MiB→4.7–7.6 MiB; string group 180.3 MiB→~135 MiB. A first run exposed a real concurrency bug (shared query-id plus racing global mark-cache drops), fixed via explicit per-job query ids and one serial cache drop. The map layout did not hit error 243 here because host disk has space (that failure is tmpfs-specific, per G2), but still costs far more in storage and reads. This is physical-feasibility evidence on a synthetic profile with a single client, **not** a production capacity sign-off: the 514/728 eight-workload API matrix under concurrency 1/4/8, real long-tail data and the default-off reader switch remain separate gates.
- Equivalence: the extended 18-shape matrix plus mixed-winner and lexical edge-case tests stay green at every stage.
