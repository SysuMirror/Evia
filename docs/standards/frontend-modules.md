# 前端模块职责与依赖

按状态所有权、业务行为和修改原因划分模块。页面入口负责组合界面；请求生命周期、可编辑草稿和结果展示分别维护自己的约束。不要用一个包含全部状态与操作的大对象替代清晰的组件接口，也不要按任意文件行数拆分同一责任。

## 包之间的方向

| 模块 | 可以依赖 | 不得依赖 |
| --- | --- | --- |
| `apps/console` | React、生成的 API 客户端、共享设计组件、本应用业务模块 | 测试夹具作为生产功能 |
| `packages/design-system` | React、主题与原生控件、独立图表能力 | `apps`、API 客户端中的业务类型与请求 |
| `packages/api-client` | 生成契约、浏览器 HTTP 能力 | React、设计组件、`apps` |
| `packages/sdk`，当其存在时 | 框架无关的 SDK 能力 | React、设计组件、`apps` |

这些方向也约束类型依赖。设计组件接收展示所需的数据，而不是导入项目、会话或查询契约。API 客户端不拥有组件、焦点或页面状态。图表使用 `@evia/design-system/charts` 独立入口，业务页面按需加载；普通控件继续使用自建组件。

## 保存分析的公开入口

| 入口 | 对外契约 |
| --- | --- |
| `saved-analyses.tsx` | `SavedAnalysesPage`，组合当前项目、环境与会话中的工作区 |
| `saved-analysis-editor.tsx` | `SavedAnalysisEditor` 与其 props，受控定义、只读/禁用状态、有效性和未应用修改通知 |
| `saved-analysis-run.tsx` | `SavedAnalysisRun`、`SavedRunWork`，以及保留兼容性的纯结果图表转换导出 |
| `saved-analysis-model.ts` | 纯定义检查、JSON 解析、固定版本与字段说明，不发请求、不拥有 React 状态 |

页面、测试和其他业务模块通过适合其用途的入口访问功能。内部子模块不得反向导入自己的组合入口；共用类型放在职责内的 `types.ts`，并使用 `import type`。不要为方便而建立把所有内部组件和控制器重新导出的总入口。

### 工作区与持久化生命周期

`saved-analyses/` 的依赖方向是入口 → 展示组件与组合控制器 → 各职责 hook → API 客户端、共享授权与导航能力。

- `use-controller.tsx` 连接导航、未保存保护和各职责的完成通知，不重新保存各 hook 已拥有的状态。
- `use-scoped-request.ts` 拥有同步请求锁、AbortController、当前授权令牌和失权处理。异步完成必须仍属于当前项目、环境和会话，才能更新状态、缓存或通知。
- `use-draft.ts` 区分本地定义与已保存修订，保留创建请求的幂等载荷，并支持读取远端后继续本地编辑或采用远端内容。失败不能覆盖输入。
- `use-publication.ts` 拥有已保存草稿的校验结果、依赖确认和发布尝试。未知发布结果必须保留原始请求标识、计数与校验摘要，关闭弹窗后仍能恢复同一次尝试。
- `use-history.ts` 拥有资源与版本的有界读取、数字版本选择和最后展示的不可变版本。加载另一个版本时，不卸载当前查询结果或替换其执行快照。
- `draft.tsx`、`draft-recovery.tsx`、`history.tsx`、`list.tsx`、`publication-review.tsx` 通过明确 props 展示对应状态与操作，不自行写入服务端或复制控制器状态。

### 编辑器

`saved-analysis-editor/` 按编辑行为分工：`use-section-editor.ts` 拥有未应用的节内副本、完成校验与放弃确认；`section-application.ts` 执行节内定义检查；`use-editor-catalog.tsx` 只读取授权范围内的已发布目录；`use-section-focus.ts` 管理动态控件后的焦点归属。字段节接收候选配置、字段和回调，不直接保存、发布或运行查询。

高级 JSON 和未展示的合法字段必须保留。编辑器内部的节表单不放入页面保存表单，避免嵌套提交。更改字段、选择时间预设和应用配置均不得暗中执行查询。

### 执行与结果

`saved-analysis-run/` 的方向是运行入口 → 执行 hook、时间控件、结果展示 → 纯结果转换与共享图表。

- `use-execution.ts` 拥有固定发布版本的入队、原键重试、取消、轮询、到期和失权处理。不能从实时编辑中的草稿重新构造已提交版本。
- `time-controls.tsx` 检查真实执行范围和时区；编辑范围只改变待提交条件。
- `result-chart.ts`、`result-labels.ts`、`result-table.tsx` 依据已提交定义与实际返回列解释结果，保留分组存在性、显式空值、缺失和数值精度。
- `result-presentation.tsx` 展示执行快照、状态、精度、覆盖信息和完整结果表；图表失败仍保留可读的结果。它不负责创建查询或访问实时表单状态。

## 自动检查与限制

运行 `node tooling/check_boundaries.cjs` 检查包方向和本地运行时导入循环；运行 `node --test tooling/check_boundaries.test.cjs` 验证检查器的回归夹具。夹具在系统临时目录创建，结束后清理，不进入生产源码。

检查器使用已安装的 TypeScript 读取仓库 `tsconfig.json`，按其路径别名和模块解析配置解析源模块及其本地依赖，包括工作区包入口。类型导入、类型重导出和 `import()` 类型表达式仍受包方向约束；循环图根据配置下的编译输出在内存中建立，不写出构建文件。因此整条 `import type`、混合命名绑定和仅用于类型位置而被编译器移除的绑定不会产生伪运行时边。开启 `verbatimModuleSyntax` 后仍被保留的空命名导入具有模块副作用，按实际输出处理。

静态导入、重导出、字面量动态 `import()` 和字面量 `require()` 纳入分析。计算得出的模块名，例如 `import(name)`、带插值的模块路径，以及别名调用的加载函数无法由此检查器解析；这类代码需要显式审查，不能把检查通过当作已经分析其依赖。检查器不分析第三方包内部循环，也不替代 TypeScript 的名称/类型检查、打包检查或浏览器验证。

生产入口不得导入 `tests/components` 等独立交互夹具。夹具中的计数器、延迟请求和测试开关仅用于验证状态，不是生产路由或服务实现。当前边界检查不等于完整的生产入口可达性审计；生产构建入口和浏览器夹具仍需分别验证。

已有循环必须先报告并按状态或类型所有权消除。当前检查器没有文件、包或循环豁免，也没有文件行数门槛。
