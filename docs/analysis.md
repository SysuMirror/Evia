# Analysis service

The implemented service accepts the typed requests in `contracts/query/query-request.schema.json`. It provides durable asynchronous jobs for event details, trends and aggregate metrics, raw-identity journeys, ordered funnels, and calendar-cohort retention matrices. SQL text, database names, arbitrary functions, and client-supplied resolved field types are never request inputs. Property references must name an event, an immutable schema version published in the requested environment, and a field in that schema. Values are bound through ClickHouse HTTP parameters.

A management session or independent machine credential determines the actor. PostgreSQL checks current human membership or exact machine credential authority when submitting, reading, canceling and publishing results. Owners/editors can access raw details; viewers are restricted to aggregate requests without raw identity access. Machines require `queries.run` to submit/cancel their own work, `queries.read` to read, and additional `queries.raw.read` for raw events, journeys or identity-bearing fields/filters. The classifier examines the full request, not just its query kind. Workers retain the originating credential through claim, lease checks and completion; replacing it does not revive revoked unfinished work. Completed results use the current reader's authority and remain available to other authorized project readers. A source write credential grants no analysis access. See [machine access](machine-access.md).

## Discovery and validation

Session- or machine-authenticated `GET analysis-capabilities`, `GET analysis-catalog?environment=...` and `POST query-validations` are implemented beneath the project API path. They discover the supported grammar and published typed property subset, or validate a complete request without scanning facts or creating a query job. `execution_available` reports configured execution support, not dependency health. Validation returns canonical request/dependency hashes; `event_keys` and unselected `all_events` remain unfixed across schema versions. A property dependency does not pin the fact selection. Execution always reauthorizes and resolves definitions again. Details, catalog state and cursor semantics are in [reporting discovery](reporting-discovery.md).

## Query semantics

- Time ranges are half-open `[from,to)`. Requests use RFC3339 timestamps; an IANA timezone controls explicit trend buckets. A trend without an interval aggregates the entire range. Current query policy accepts years 1970 through 2100.
- Event details, trends, and journeys can pin facts with `event_versions: [{"event_key":"forum_page_view","schema_version":1}]`. The nonempty selection allows at most 20 distinct events, with one immutable version per event; duplicate pairs and multiple versions of the same event reject until compatibility rules exist. Each selected version must belong to a release in the authorized project and requested environment, including count/UV queries without property references. Historical published versions remain queryable without current ingestion readiness or activation. Property references must belong to the pinned selection. The generated fact predicate matches exact event/version pairs before aggregation. `event_keys` and `event_versions` cannot appear together; existing `event_keys` queries continue to include all schema versions of each key. Funnels reject `event_versions` because their ordered steps already pin each event version.
- PV is `count` over the published event explicitly chosen to represent one page view. The console requires that selection and preserves the chosen PV meaning with the submitted result snapshot; an arbitrary interaction count is not automatically a page-view count. It does not create or assume an available `sys.page_view` runtime definition. UV is `unique` with an explicit `uid` or `anonymous` subject. UID UV excludes absent and empty UIDs. Anonymous UV counts raw anonymous identifiers. Daily UV values must not be added to obtain whole-range UV.
- Exact aggregation is the default. Approximate unique counts and approximate percentiles (p50/p90/p95/p99, evaluated with quantileTDigest rather than the exact quantileExact) must be requested explicitly; result metadata reports approximate accuracy when any requested metric uses it. Numeric aggregates omit missing, null, and wrongly typed values; a numeric aggregate without observations is null rather than an invented zero. Count and unique counts over no observations are zero.
- Properties remain scoped to their event and schema version. Comparisons do not coerce false into zero or missing into a default value. `is_present` includes an explicit null, while `is_missing` does not. Property grouping returns a corresponding `group_N_present` column to distinguish absent values from explicit nulls.
- Negated comparisons are the closed set `not_in`, `not_prefix` and `not_contains` (array fields additionally accept `not_contains`). Each keeps the identical scope/presence/validity guard as its positive counterpart and only inverts the inner test, so absent keys, explicit nulls and wrongly typed values stay excluded; an empty `not_in` matches every present/valid row rather than collapsing to a constant. There is deliberately no generic `not` node: wrapping the whole guarded predicate in SQL `NOT` would fold missing rows back into the result and break the three-valued-logic invariant.
- A UID journey includes only facts with that original UID. It does not attach earlier anonymous events or another account sharing a device. Anonymous queries use the raw anonymous identifier, including authenticated facts that retain that identifier; this is a device identifier, not a resolved person.
- Ordered funnels permit other events between steps, count each subject at most once per reached step, and use one event for at most one step. Every reached step must fit within the window from a candidate first step. Later first-step candidates are retained. Optional entity constraints require matching scalar values across their specified steps. Equal timestamps advance only with the same source, nonempty session and tab, and increasing sequence. Otherwise, timestamps must increase.
- Retention builds a calendar-cohort matrix for an explicit `uid` or `anonymous` subject. Each subject enters one cohort in the timezone-aligned day or Monday-starting week of its earliest pinned `start_event`; pinned `return_event` occurrences are counted per offset period relative to that cohort. Offset zero is the entry itself and always retains at 1.0; return events before entry or at/beyond the requested period count are ignored. The `uid` and `anonymous_id` columns are selected exclusively by the chosen subject, so the two matrices never mix identifiers. Both boundary events pin `event_key` plus immutable `schema_version` and accept the same bounded filter DSL; top-level `event_keys`, `event_versions`, grouping, metrics and intervals are rejected. Granularity is the closed set `day`/`week`/`month` with 1–12 periods. Day/week time ranges cannot exceed `periods × granularity` (at most 84 days); month cohorts align to the first timezone-local calendar day and the bounded raw-pull window uses a conservative 31-day-per-period upper bound (the evaluator itself counts whole calendar months, not elapsed days). Saved analyses do not accept retention; the template surface stays limited to trend and funnel.
- Subject segmentation (`segment`) partitions an explicit `uid` or `anonymous` population into mutually exclusive groups. Unlike trend `group_by`, which is event-level and can place one subject in several groups, each subject receives exactly one label: the scalar field value on its earliest matching pinned event. Missing, null or blank values join a fixed `__missing__` group. The grouping field must be a scalar (string, boolean, integer or number); arrays and datetimes are rejected. Output rows report the group value, distinct subject count and share, ordered by subject count descending then value ascending. The time range is bounded to seven days and the raw pull to 100,000 rows. Saved analyses do not accept segmentation.
- Path aggregation (`path`) counts the ordered event sequences subjects actually traverse. Each subject contributes at most one fixed-length (`depth` 2–8) sequence: either the events following its earliest optional pinned `start_event`, or its first in-window events when no start is pinned. Subjects with fewer than `depth` events are excluded. Equal-time events use the same causal session ordering as funnels. An optional `collapse_repeats` flag folds adjacent identical event keys into one node before start-pin and depth extraction; when omitted the raw sequence and existing results stay byte-stable. Output rows report the ordered `event_key` path and distinct subject count, ordered by count descending then path ascending, within a seven-day, 100,000-row bounded pull. Saved analyses do not accept path aggregation.
- Last-touch attribution (`attribution`) credits each converting subject once, at its earliest conversion, to the causally latest matching touchpoint inside a bounded lookback window (1–604,800 seconds). The conversion and 1–8 touchpoints pin immutable event versions; a touchpoint pair may not repeat or reuse the conversion pair. Converters without an in-window touchpoint land in a fixed `__direct__` bucket so the converting population is never silently dropped. Output rows report the touchpoint, distinct converting-subject count and share, ordered by count descending then touchpoint ascending, within a seven-day, 100,000-row bounded pull. The model is an explicit closed set: `last_touch` credits the latest in-window touchpoint, `first_touch` the earliest, `linear` splits each converter's unit weight equally across its distinct in-window touchpoints, `position_based` applies U-shaped weights (the first and last distinct in-window touchpoints each receive 0.4, the middle touchpoints share the remaining 0.2 equally; with two touchpoints they split 0.5/0.5 and a single touchpoint receives full weight), and `time_decay` applies exponential half-life weights `0.5^(delta/half_life)` from a bounded `decay_half_life_seconds` parameter before normalizing within the subject. The weighted models (`linear`, `position_based`, `time_decay`) additionally report a fractional `credit` column; converters without an in-window touchpoint stay in the fixed direct bucket. Saved analyses do not accept attribution.

The read view deduplicates by project, environment, source, and event ID before analysis predicates or aggregates. Identical IDs from different sources remain different facts. The winner order is receipt time, canonical content hash, effective occurred time and effective event time. This avoids depending on eventual background merges for exact counts.

Trend queries use the same tuple-valued winner selection with only the columns needed by the request. Migration 004 supplies compact hash bytes and effective timestamps; historical parts remain correct before explicit materialization, but their read cost is not yet reduced. A necessary UID or anonymous-ID equality can first locate candidate source/event pairs through migration 005's projections. Every raw version of those pairs still participates in winner selection, and the complete event, version, time, identity and property predicates remain outside it. Projection availability affects cost, not the definition of a matching fact.

The trend winner aggregate groups by source and event ID within the fixed authorized project and environment. These two scope values are bound once and reconstructed as output constants, avoiding repeated strings in each aggregation key. Raw and candidate scope columns are explicitly qualified so an outer constant alias cannot replace the stored authorization predicate. This optimization does not combine projects, environments or sources.

Numeric property guards recognize ClickHouse JSON categories `Int64`, `UInt64` and `Double`. Decimal and exponent values participate in numeric aggregation and comparisons; strings and booleans are not scalar numbers. Properties continue to use the original document. A proposed per-property layout was deferred because the database's raw-extraction functions normalize number tokens; the [property read design](plans/property-read-layout.md) records the compatibility requirements.

## Timestamp deployment order

Apply the explicit ClickHouse migration chain before deploying the corresponding sink. `001_event_facts.sql` remains unchanged. `003_event_precision.sql` retains millisecond partition/sort columns and adds two nullable nanosecond payload columns. The view exposes their effective values under the existing `occurred_at` and `event_time` names as non-null `DateTime64(9)`.

Old stored millisecond values remain millisecond values. Lost historical precision is not reconstructed. New writes carry nanoseconds through the queue, sink, view, query comparison, and funnel ordering. Legacy-writer rollback remains compatible through defaults and view fallback. The new sink rejects missing precision columns instead of relying on a server setting that might silently skip unknown input fields. The migration is safe to reapply, checks unsupported legacy dates before DDL, and does not replace the raw table or its keys. The extra timestamp payloads and null maps add storage cost. Pipeline timestamps outside the supported 1900-01-01 through 2262-04-11T23:47:16.854775807Z range are rejected before queue publication or quarantined when decoding malformed queued records.

Current query readers additionally require `004_compact_winner_columns.sql` before deployment. Apply `005_identity_projections.sql` for selective identity access paths. Follow the [compact-column](runbooks/compact-winner-upgrade.md) and [identity-projection](runbooks/identity-query-upgrade.md) upgrade procedures for bounded historical materialization, disk reserves and rollback. These migrations add no implicit startup rewrite. The query role needs read access to the configured database's `event_facts_raw` as well as `event_facts`; clients still cannot submit raw SQL.

## Durable jobs and budgets

Jobs are queued in PostgreSQL, claimed with a generation-numbered lease, and published with a compare-and-swap check. An expired or canceled worker cannot publish a result. Execution leases last 45 seconds, queries have a 30-second execution deadline, and abandoned leases can be reclaimed within a three-attempt budget. Queue admission is serialized per project; at most four jobs execute and 32 wait per project. The configured number of worker loops supplies the process-wide limit. `Worker.Run` returns on storage errors, so its caller must supervise it with bounded restart backoff.

Cancellation changes durable job state and blocks later publication. Workers inspect their leases every 250 milliseconds. Cancellation also interrupts local funnel computation, closes the readonly HTTP query, and attempts to terminate that execution ID in ClickHouse. The ClickHouse execution deadline bounds remote work if a network failure prevents cancellation confirmation.

| Budget | Current limit |
| --- | --- |
| Trend time range | 31 days |
| Event, journey, or funnel time range | 7 days |
| Filter depth / total nodes | 8 / 100 |
| Event keys or pinned event versions / groups / metrics | 20 / 3 / 10 |
| Funnel steps / window | 2–8 / at most 7 days |
| Retention granularity / periods | day, week or month / 1–12; day/week time range at most periods × granularity (84-day ceiling), month uses a conservative 31-day-per-period scan bound (up to 372 days) while cohorts align to calendar months |
| Segment time range / input | 7 days / at most 100,000 raw rows; scalar grouping fields only |
| Path depth / input | 2–8 events / at most 100,000 raw rows; optional pinned start event |
| Attribution window / touchpoints | 1–604,800 seconds / 1–8 pinned touchpoints; last-touch model |
| Result rows | Request limit 1–500; default 200 |
| Published result JSON | 1.5 MiB, within the PostgreSQL 2 MiB storage guard |
| ClickHouse rows / bytes read | 2 million / 256 MiB |
| ClickHouse query memory / threads | 512 MiB / 2 |
| Funnel input | At most 100,000 rows and the 4 MiB response budget |
| Funnel candidates | 10,000 live states per subject; 1 million cumulative retained states |
| Retention input | At most 100,000 rows and the 4 MiB response budget; at most 12 cohort rows |

Exceeding a result or execution budget returns an explicit failure instead of publishing a silently shortened aggregate or timeline. Queued jobs have a ten-minute wait deadline. Results expire after one hour; jobs expire after 24 hours, with bounded removal of expired records after a further hour. Reading an expired result cannot recover its stored event data.

Per-query memory limits are ceilings, not reserved memory. ClickHouse can reject concurrent executions against its server-wide limit even when each query stays below 512 MiB. Worker concurrency must account for every process sharing that server, background merges and other database workloads. The current process worker count and per-project queue bounds do not provide a cluster-wide memory admission controller. Measure concurrent outcomes explicitly; do not infer them from successful serial queries or automatically raise budgets after a resource rejection.

## Result snapshot continuation

The completed result is an immutable stored snapshot (at most 500 rows / 1.5 MiB). `GET .../queries/{query_id}/result` accepts optional `limit` (1–200) and `cursor` query parameters to read that snapshot in bounded pages. Omitting both returns the full snapshot exactly as before, so existing readers stay byte-stable. A first paged request returns up to `limit` rows and, when more rows remain, a signed `next_cursor`; repeating the request with that cursor returns the next page until `next_cursor` is null.

Cursors are HMAC-signed, bound to the actor, project and query result scope, embed the page offset and page size, and expire after 24 hours. A tampered, expired, foreign-scope or malformed cursor, an out-of-range offset, or a `limit` that differs from the first page fails closed with a 400 before the stored snapshot is read. The console requests a bounded first page for raw event and journey reads and offers a load-next-page control; aggregated kinds keep reading the full snapshot. This paginates an already-materialized snapshot only; the request-body cursor for engine-level timeline continuation remains explicitly unsupported.

## Evidence and remaining scope

Unit tests cover strict DSL rejection, pinned selection bounds and exact pair parameter binding, numeric precision declarations, Unicode UID limits, ordering, and cancellation of local computation. Retention unit tests cover the cohort matrix arithmetic, Monday-aligned timezone weeks, period-zero semantics, out-of-range offsets, earliest-start pinning and the full validation closed set. Segmentation unit tests cover unique subject ownership via the earliest event value, missing-group routing, scalar rendering, share arithmetic and the scalar-only compile-time field guard. Path unit tests cover ordered sequence aggregation, pinned-start extraction, equal-time causal ordering, short-subject exclusion, the validation closed set and the mutually exclusive subject-column planner; the ClickHouse integration suite asserts distinct paths, subject counts, pinned-start tails and project isolation against the migrated view. Attribution unit tests cover last-touch selection, the direct bucket, the lookback boundary, equal-time causal ordering, the validation closed set and marker-column planning; the ClickHouse integration suite asserts credit counts, direct-bucket fallback, window collapse and project isolation against the migrated view. PostgreSQL integration tests cover admission races, lease generations, revocation, cancellation/completion races, result expiry, published field resolution, all selected versions' environment membership even for count/UV without properties, durable selection preservation, and rollback when completion audit fails. ClickHouse integration tests use isolated databases and actual migrations to verify mixed-version count/exact UV selection and existing cross-version event-key semantics, dedup before filters/counts, metric values, missing/null/false/zero/array behavior, identity boundaries, context links, funnel ordering, the end-to-end retention matrix against the migrated view, nanosecond upgrade compatibility, and disappearance of an actually running canceled query.

`data_watermark` is the latest received timestamp actually observed by that query, or null for no observations. It is not a completeness watermark. Coverage remains provisional, identity resolution is not applied, sample rate is one, and cache-hit metadata is false. No cache, settlement process, identity graph, or production capacity has been demonstrated by these tests.

Resolved-person queries and identity revisions reject explicitly until a real versioned identity graph exists. The request-body cursor for engine-level timeline continuation still rejects explicitly. Result snapshot reads now support signed continuation cursors, as described in the result snapshot continuation section. Retention, subject segmentation, path aggregation and last-touch attribution cover uid and anonymous populations as ad-hoc jobs with a console workspace; saved-analysis templates, cross-identifier identity merging, heatmaps, session replay, exports, and broader lifecycle operations remain outside this implementation.

Run dependency tests with the repository-compatible Go toolchain and explicit test configuration; missing dependencies fail rather than silently substituting mocks:

```sh
./deploy/dev-env run /tmp/evia-pipeline.env -- \
  go -C backend test -race -tags=integration \
  ./internal/analysis ./internal/pipeline -count=1
```

PostgreSQL tests additionally require `EVIA_TEST_DATABASE_URL` and use isolated schemas, never global table truncation.
