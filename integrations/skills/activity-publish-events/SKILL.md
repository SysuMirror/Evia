---
name: activity-publish-events
description: Register, validate, publish and activate a complete business event set through scoped Evia management APIs.
---

Use after a business event plan exists and the user authorizes integration. Read [helper and credential rules](../../README.md). The helper issues individual requests; it does not automate publication. Use the target deployment's authoritative OpenAPI; never invent an endpoint or use direct database writes. Machine authentication must be implemented in that deployment. Missing/invalid machine authentication stops dependent calls; do not borrow an owner session or collection secret.

Discover `GET /api/v1/machine-identity` with the provided Bearer machine credential using `tooling/activity_api.py`. Bind the explicit project/environment to that response. Check expiry and required permissions: `project.read`, `catalog.drafts.read`, `catalog.drafts.write`, `catalog.releases.read`, `catalog.releases.publish`, `catalog.releases.activate`, `queries.read` for the active analysis catalog, and `sources.read` plus `sources.write` if source creation is needed. Draft permissions are project-wide; the principal's environment scope does not isolate drafts. Do not infer additional authority from API resource IDs, public write keys or analysis capabilities. Never issue/revoke/rotate a management credential as an integration shortcut.

Let `P=/api/v1/projects/{project_id}`. For every paginated read, follow bounded scoped cursors until complete and reject partial evidence. Keep private outputs and stable retry inputs in an ignored private directory. Do not print credentials, response bodies or business data.

1. Read `GET P`, `GET P/release-activations?environment=…`, all `GET P/analysis-catalog?environment=…` pages, and relevant `GET P/event-definitions?environment=…` plus `GET P/event-definitions/{event_key}/draft`. Analysis catalog contains historical versions; use `active:true` for current membership. Re-read activation after pagination and restart if changed. There is no immutable release-manifest read endpoint to assume.
2. Compare the complete desired set with current active membership. Assemble the local snapshot described in README and run the membership diff helper. Every removed key must match `removed_event_keys` exactly. Compare retained immutable definitions through `GET P/event-definitions/{event_key}/versions/{schema_version}` and current drafts. Present consequential differences within the user's authorized scope. Never silently carry pending unrelated draft edits into a release. If a retained active definition no longer matches its draft, resolve that conflict explicitly before publication.
3. Create missing keys using `POST P/event-definitions` with `{event_key,display_name,description?}`. Read drafts; update using `PATCH P/event-definitions/{event_key}/draft` and `If-Match: "revision"`. Send only DraftInput fields: `display_name,schema,field_metadata,trigger,allowed_source_kinds,fact_kind,example_properties`. `schema` replaces the whole schema; omitted optional metadata retains prior values. Omit local `implementation_sites` and event key from DraftInput. On revision conflict, read and compare again; never force overwrite.
4. Validate every exact draft using `POST P/event-definitions/{event_key}/validate` with `{draft_revision,sample_properties}`. Require `valid:true`, inspect compatibility and issues. Resolve breaking changes within authorized scope before continuing. Local structural validation does not replace this step.
5. Re-read the actual active revision. `POST P/releases` with a stable `Idempotency-Key` and `{environment,expected_active_revision,events:[{event_key,draft_revision}]}` containing the **entire intended set** in deterministic key order. The server assigns/reuses immutable schema versions. Preserve exact request content and key for an ambiguous retry. A different request requires a new key and fresh comparison.
6. Poll `GET P/releases/{release_id}` with a caller-defined deadline/backoff. Require `state:"published"` and server-derived `ingestion_ready:true`. The real release-delivery worker must obtain its proof through Kafka and ClickHouse. Never write readiness, insert proof rows or treat `published` alone as ready. Timeout/failure is an incomplete integration result.
7. Activate with a separate stable `Idempotency-Key`: `POST P/release-activations` with `{environment,release_id,expected_active_revision}`. Preserve the actual activation precondition. Conflict requires a new read/diff. Verify `GET P/release-activations?environment=…` matches the returned release revision. Readiness is a lease and can expire after activation.
8. Reuse an appropriate browser source, or create one with `POST P/sources` using `{name,environment,kind:"browser",allowed_origins:[exactOrigin]}`. An origin contains scheme/host/port only; no wildcard, path, query or credentials. Follow `GET P/sources/{source_id}` until `application_state:"applied"` with a bounded deadline. Changes use quoted revision comparison. Do not rotate/disable an existing source without task authorization. Keep the browser write key private during setup and expose only that public browser key in application configuration.

Record separate actual results: definitions validated, immutable release built, delivery ready, activation confirmed, source applied. None proves application events reached storage. Continue with `activity-integrate-verify`. Return precise partial state and recovery inputs if a step fails; never mark the manifest published or integration complete on a timeout.
