---
name: activity-integrate-verify
description: Install the local Evia browser SDK, emit published business events from application code, and verify their actual stored facts.
---

Use after definitions, active ready release and browser source are confirmed. Read [public helper guidance](../../README.md) and the SDK documentation supplied with the intended Evia version. Follow business-repository instructions. Complete authorized code changes and verification; report unavailable infrastructure precisely.

The SDK currently ships as workspace source/local archive. Build it in its Evia checkout with `pnpm --filter @evia/browser-sdk build`, then `pnpm --filter @evia/browser-sdk pack --pack-destination /tmp/evia-sdk-package`. Use the checkout's configured pnpm version. Inspect the resulting archive and install that supplied local tgz with the business repository's package manager. Do not claim a registry release exists. Do not copy internal engineering files or the platform repository's AGENTS.md. Preserve the business lockfile/dependency conventions.

Initialize one `createEviaClient({endpoint,writeKey,projectId,environment})` per intended browser scope and await `init()`. Only the browser source's public write key goes into the frontend. Machine tokens, server secrets and platform session cookies never do. Public config/collection use the browser's exact Origin, not the machine identity API. Verify public config project/environment/release and selected event versions through the real browser. `init()` alone does not establish ingestion.

Implement explicit `emit(eventKey,properties)` calls at the manifest's evidence sites. Do not add automatic DOM listeners, URL/query harvesting or business facts inferred from UI text. Await successful application outcomes for confirmed actions; a browser can emit only its allowed fact/source kinds. Navigate explicitly from route code with safe templates, then explicitly emit the registered page event. `navigate()` emits no event. `identify(uid)` affects future events only and performs no historical merge. Call `reset()` at logout; call `destroy()` at teardown. Preserve queued identity snapshots, default queue limits and immutable retries.

Run relevant business build/tests and exercise actual browser/CORS behavior at the configured origin. Use a small synthetic verification session and allowed properties/identity; do not add arbitrary properties absent from published schemas or replay real user data. Capture each returned emission's `eventId` and individual `result`. `flush()` has bounded turns and may leave pending work; inspect each result. An accepted receipt proves durable queue admission, not storage. Never treat HTTP 202 alone, a send attempt, a sendBeacon result, or zero pending events as ingestion proof.

Verify actual storage through the scoped machine helper:

1. Discover machine identity and require `queries.run`, `queries.read`, `queries.raw.read` for raw verification; catalog discovery additionally needs its documented read permissions. Inspect `GET P/analysis-capabilities` and `GET P/analysis-catalog?environment=…`. `execution_available` reports configuration, not worker/ClickHouse health. Do not substitute an owner's credential when scope is insufficient.
2. Build an actual QueryRequest with `kind:"events"`, explicit environment, `timezone:"UTC"`, a short absolute half-open `time_range`, exact `event_versions:[{event_key,schema_version}]`, an existing allowed synthetic marker filter or dedicated raw identity filter, and a small limit. One query selects at most 20 event versions; verify larger plans in bounded groups. Do not invent an event-ID lookup or verification endpoint. Optional `POST P/query-validations` validates grammar/permissions without reading facts.
3. `POST P/queries`, poll `GET P/queries/{query_id}` using `poll_after_ms` with a total deadline, then `GET P/queries/{query_id}/result`. Require a succeeded job and an untruncated set containing the expected facts. Failed, canceled or expired jobs do not establish visibility. Visibility can lag acceptance; bounded fresh queries may be necessary. Never change worker state or results to pass.
4. Compare actual stored `event_id` values with captured SDK IDs, require each expected source/event pair exactly once, and compare event key, schema version, source ID, relevant synthetic properties, UID/anonymous ID and navigation context. Inspect result truncation/coverage metadata; a data watermark does not prove all partitions are complete. Verify planned calls by exercising their real application paths. Synthetic SDK-only calls prove the delivery path, not those code sites.

Save a sanitized report containing deployed revision where available, exact scope, tested routes/actions, expected/accepted/stored counts, query IDs, time window, failures and remaining coverage. Keep credentials and raw event payloads out. Distinguish implementation/build success, durable acceptance and observed facts. Report unexercised event paths and missing raw query permission as unverified. Do not claim production capacity, identity merging or cross-document session continuity from this functional check.
